# MORPHEUS Backend API — Implementation Reference

This documents the concrete implementation of the contract requested in
`MORPHEUS_BACKEND_API_REQUIREMENTS.md`. That document was transport-agnostic
by design; this one describes the actual delivered transport, so a new
frontend (including a UI generated by an external design tool) knows
exactly what to import and call.

**Transport:** this is a Python application with no client/server split
and no network boundary — the backend is an in-process Python class,
consumed via direct method calls and plain-callback event subscriptions.
This is a valid transport under the requirements doc's own §3.1 ("local
API, IPC, native bindings, ..."). If a future frontend runs in a
different process or language, this class is the natural place to put
a thin RPC/IPC wrapper around — its methods and events already map
1:1 onto the requested contract.

**Module:** `tools/ble_client/backend.py` — class `MorpheusBackend`.
**Pairing internals:** `tools/ble_client/pairing_backend.py` (imported
lazily by `backend.py`; see §6).

---

## 1. Quick start

```python
from backend import MorpheusBackend, TrainingMode

be = MorpheusBackend()

be.on_connection_changed(lambda info: print("connection:", info))
be.on_keyer_word(lambda evt: print("word:", evt))
be.on_training_state(lambda state: print("training:", state))
be.on_pairing_state(lambda evt: print("pairing:", evt))
be.on_error(lambda err: print("error:", err))

be.connect()                      # scan-then-connect, address optional
be.start_training(TrainingMode.KOCH)
be.key_down(); be.key_up()
be.stop_training()
be.disconnect()
```

## 2. Threading model (read this before wiring up a UI)

- `connect()` / `scan()` spawn a background thread running its own
  asyncio event loop (bleak). `disconnect()`, `key_down()`, `key_up()`,
  `start_training()`, `stop_training()`, `confirm_training()` all
  marshal onto that same loop internally — call them from any thread.
- `start_pairing()` spawns a **second**, independent background thread
  with its own asyncio loop (dbus-next), matching the reference
  implementation's separation of "pairing session" from "GATT
  session" — they are unrelated processes in BlueZ.
- Every `on_*` callback is invoked **directly on whichever background
  thread produced the event** — never on the thread that called
  `connect()`/`start_pairing()`/etc, and never on a dedicated "event
  thread". A UI framework with thread affinity (Qt, most GUI
  toolkits) **must** marshal these calls onto its own UI thread. See
  §7 for how the Qt frontend in this repo does it (Qt signals, which
  auto-queue across threads for free).

## 3. Data contracts

All are plain `@dataclass` instances in `backend.py` — no serialization
layer is imposed; a frontend in the same process uses them directly,
a future out-of-process frontend would serialize them (e.g. to JSON)
at its IPC boundary.

```python
@dataclass
class ConnectionInfo:
    state: ConnectionState
    deviceName: str | None = None
    deviceAddress: str | None = None
    statusMessage: str | None = None

@dataclass
class KeyerWordEvent:
    word: str
    wpm: int
    mode: str            # "STRAIGHT" | "PADDLE"
    timestamp: int       # device uptime ms, NOT wall-clock

@dataclass
class TrainingState:
    active: bool
    mode: str | None = None
    phase: str | None = None
    target: str | None = None
    correct: int = 0
    attempts: int = 0
    kochLevel: int | None = None
    adaptiveWpm: int | None = None
    examScorePercent: int | None = None
    examPassed: bool | None = None
    examCorrectCount: int | None = None
    examTotalCount: int | None = None

@dataclass
class PairingEvent:
    type: PairingEventType
    devicePath: str | None = None
    passkey: int | None = None
    errorCode: str | None = None
    errorMessage: str | None = None

@dataclass
class BackendError:
    code: str
    message: str
    severity: str = "ERROR"      # ERROR | WARNING | INFO
    recoverable: bool = True
    operation: str | None = None

@dataclass
class Capabilities:
    connection: bool = True
    pairing: bool = False
    keyer: bool = True
    training: bool = True
    statistics: bool = False
    connectivityManagement: bool = False
    profiles: bool = False
    settings: bool = False
    diagnostics: bool = False
    tools: bool = False
```

Enums (`ConnectionState`, `KeyingMode`, `TrainingMode`, `PairingEventType`,
`Severity`, `ErrorCode`) are `str`-valued `Enum` subclasses using the
exact string values from the requirements doc (`.value` gives you the
plain string, e.g. `ConnectionState.CONNECTED.value == "CONNECTED"`).

## 4. Event subscription API

```python
be.on_connection_changed(callback)  # callback(info: ConnectionInfo)
be.on_keyer_word(callback)          # callback(evt: KeyerWordEvent)
be.on_training_state(callback)      # callback(state: TrainingState)
be.on_pairing_state(callback)       # callback(evt: PairingEvent)
be.on_error(callback)               # callback(err: BackendError)
```

Multiple callbacks may be registered per event type; there is no
`off_*`/unsubscribe yet (not required by any current consumer — add it
if a frontend needs dynamic subscription lifecycles).

## 5. Commands

```python
be.scan() -> None
be.connect(device_address: str | None = None) -> None
be.disconnect() -> None

be.key_down() -> None
be.key_up() -> None

be.start_training(mode: TrainingMode | str) -> None
be.stop_training() -> None
be.confirm_training() -> None

be.start_pairing(target_device_name: str) -> None
be.submit_passkey(passkey: str) -> None
be.confirm_pairing(accepted: bool) -> None
```

All commands are fire-and-forget (no return value): outcomes and
failures are observed exclusively through the event callbacks (§4),
per the requirements doc's "commands must not silently fail" —
`start_training("BOGUS")` emits an `INVALID_PARAMETER` error via
`on_error` rather than raising or doing nothing.

## 6. Capabilities and metadata

```python
be.get_capabilities() -> Capabilities
be.get_metadata() -> dict   # {"applicationVersion", "deviceName", "deviceFirmwareVersion"}
```

`Capabilities.pairing` is computed by actually attempting the lazy
import of `pairing_backend.py` (which itself only imports `dbus-next`
on Linux) — not by hardcoding a platform check, so it's accurate on any
future platform the app runs on. Every other flag currently defaults to
`False` — Statistics/Profiles/Settings/Diagnostics/Tools have no BLE
support in the firmware yet (see `UI_SPECIFICATION.md`), so a frontend
should treat those sections as present-but-disabled rather than hide
them arbitrarily, matching the requirements doc's "explicit capability,
not hidden."

## 7. Reference data

```python
MorpheusBackend.get_koch_sequence() -> str      # the 40-char Koch order
MorpheusBackend.get_morse_table() -> dict       # {char: ".-" pattern, ...}
```

Both are exact copies of firmware source (`core_trainer.cpp`'s
`KOCH_ORDER`, `core_decoder.cpp`'s `morseTable`), re-exported from
`protocol.py` — not derived data, not approximations.

## 8. Error codes actually emitted today

A subset of the requirements doc's full code list is wired up by the
current implementation (the rest are reserved for future use, e.g. once
Statistics/Settings get real BLE commands):

| Code | Emitted when |
|---|---|
| `DEVICE_NOT_FOUND` | `connect()`/`scan()` timed out without finding the device |
| `CONNECTION_FAILED` | the GATT connection attempt itself raised |
| `DEVICE_BUSY` | a command was issued with no active connection |
| `INVALID_PARAMETER` | `start_training()` was given a mode outside `TrainingMode` |
| `TRAINING_START_FAILED` | the device's control channel reported `{"evt":"error"}` |
| `PAIRING_UNAVAILABLE` | pairing attempted where `Capabilities.pairing` is `False` |
| `PAIRING_FAILED` | any step of the BlueZ pairing flow failed |
| `INTERNAL_ERROR` | an unexpected exception inside the backend's own async code |

## 9. What this backend intentionally does not cover

Matches `MORPHEUS_BACKEND_API_REQUIREMENTS.md` §2/§18 exactly:
client-local Games (own module, `arcade.py`, no BLE involvement at
all), client-derived keyer/training counters (computed in the UI layer
from the raw events above), and Statistics/Profiles/Settings/
Diagnostics/Tools (no device-side BLE command exists yet — see
`UI_SPECIFICATION.md` for the full field list of what those sections
need once the firmware exposes them).

## 10. Reference integration: how the existing Qt app consumes this

`ble_client_core.py`'s `BleWorker` and `ble_pairing.py`'s `PairingWorker`
are ~100-line adapters that do nothing but register `on_*` callbacks
above and re-emit them as Qt signals (which auto-marshal to the GUI
thread). A frontend built by an external tool can either:

- **reuse `MorpheusBackend` directly** (if it's also Python) and write
  an equally thin adapter for its own framework's event/threading
  model, or
- **treat `backend.py` as the spec** and reimplement an equivalent
  class against its own language/runtime, using this document plus
  `MORPHEUS_BACKEND_API_REQUIREMENTS.md` as the two source-of-truth
  references.
